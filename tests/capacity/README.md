# 后端容量测试

容量工具位于 `tests/capacity/`。测试从独立 Mac 上的原生 k6 发起，经仅监听本机的 SSH 隧道进入新后端。结果记录真实请求吞吐、完整练习成功率、异步落库和恢复情况；实测数据见[后端容量实测记录](../../docs/backend-capacity-results.md)。

## 已有结果

已完成运行的脱敏结果位于 [results/](results/index.json)，包括 [2026-11-13 的 2000 VU 结果](results/20261113-r11/report.html)。该轮持续 600 秒，15,619 条同步意图最终全部提交，完整性检查通过；严格 SLA 未通过，确认 P95/P99 为 65,208／209,713 毫秒。它验证压测器账本的最终补传，微信真机存储与重启恢复需单独验证。不同后端版本的记录按运行编号保留。

`report.py` 可直接读取 `trials/*/result.json` 或套件 `results.json`；逐次完成记录优先，缺少套件完成文件时显示未确认整套完成。导出仅包含白名单字段和匿名数值采样，私有连接、凭据、意图账本和数据库转储保存在仓库外。

## 运行条件

- 使用通过 CI 的后端版本。来源 IP 限流默认开启，由 `BACKEND_REQUEST_LIMITS_ENABLED` 控制，同一来源每 60 秒最多 60000 次；普通账号读写不设固定配额。本次工具固定使用校验过官方 SHA-256 的 k6 2.3.0。
- 本机使用 Python 3.10 及以上版本的独立虚拟环境，安装 `tests/capacity/requirements.txt` 中固定的 AsyncSSH。转发监听本机回环地址，使用指定私钥和已有 `known_hosts` 校验服务器主机密钥。
- 具备本项目后端主机的 SSH 管理权限和免交互 `sudo`。允许题小搭测试服务暂时不可用；原有数据库、队列和配置会保留。
- 连接配置、SSH 私钥、管理员凭据、学生令牌和原始运行证据存放在仓库外的权限 `700` 目录中，文件权限为 `600`。

运行目录名使用日期及可选英文后缀，例如 `20261108`。该目录的 `connection.json` 包含以下私有字段：

| 字段 | 用途 |
|---|---|
| `host`、`user`、`key` | SSH 主机、管理员和私钥绝对路径 |
| `remote_dir` | `/var/lib/qanda-capacity/<运行目录名>` |
| `k6` | 已核验的原生 k6 可执行文件绝对路径 |
| `port` | 本机隧道监听端口，例如 `18093` |
| `expected_revision` | 已成功部署并待测的完整提交 SHA |

## 数据隔离与准备

数据库保护要求使用固定库名 `qanda_backend`。准备程序停止本项目应用及原 PostgreSQL、RabbitMQ、Redis 容器，保留原卷，使用相同镜像 ID、内存限制和网络别名启动带运行标签的临时基础服务。压测数据使用独立 PostgreSQL 卷、RabbitMQ vhost 和临时 Redis。每轮恢复数据基线后只清空本次拥有的 Redis，缓存命名空间包含运行编号。原备份计时器在窗口内暂停，恢复后重启。

程序通过既有交互式首管、题库导入及测试账号接口准备数据：20 个题库，共 10000 道可作答题，覆盖单选、多选、判断、填空、简答和阅读题组。阅读材料单独占父记录，因此物理题目行数高于可作答题数。每次从快照恢复后，在隔离数据库执行 `ANALYZE`，为查询规划准备统计信息。测试账号计入统计，各用户使用独立令牌、设备和练习。测试调用范围排除邮件和微信提供端。

```sh
python3.12 -m venv "$HOME/.local/share/qanda-capacity/venv"
CAPACITY_PYTHON="$HOME/.local/share/qanda-capacity/venv/bin/python"
"$CAPACITY_PYTHON" -m pip install -r tests/capacity/requirements.txt
CAPACITY_STATE="$HOME/.local/state/qanda-capacity/20261108"
"$CAPACITY_PYTHON" tests/capacity/setup.py --state "$CAPACITY_STATE" --users 1000
"$CAPACITY_PYTHON" tests/capacity/validate.py --state "$CAPACITY_STATE"
caffeinate -i "$CAPACITY_PYTHON" tests/capacity/run.py --state "$CAPACITY_STATE" --restore
```

`setup.py` 核对已部署 SHA，安装私有运维脚本，完成单用户保存、回执、重复提交和交卷验收，再保存测试数据基线。合成题目先通过既有导入预览校验。准备失败时尝试恢复原服务，并保留私有诊断。`validate.py` 验证同一账号连续 610 次读取、130 次写入均可成功，检查认证和权限，并执行原生 k6 单用户练习。

## 加压与判定

真实学生流程从 50 个活跃用户开始，每级 10 分钟；读取、创建、同步和交卷从每秒 10 次业务操作开始，每级 3 分钟；突发创建和交卷从 100 人在一秒内发起操作开始。稳定时逐级翻倍，首次失稳后每级增加 25%，没有固定的请求量上限。临界区间缩小到约 10% 并复测，最终学生流程稳定档运行 30 分钟。性能修复后的套件可用 `--start-users 400` 从已发现问题的负载档开始；单场景可用 `--scenario journey --target 400` 复测。

A 组保留来源 IP 限流，B 组在隔离测试中关闭该层保护；两组的账号读写均不设固定配额，节点并发准入使用相同配置。来源拒绝的 429、入口拥挤的 503 及实际完成的业务操作分别统计。测试结束后恢复原来源 IP 配置。

HTTP 吞吐与业务操作速率分别统计。交卷吞吐场景包含创建练习的实际成本；集中交卷场景使用提前创建的独立练习。真实学生场景保留思考时间、六十秒加零至十秒错峰同步、一／二／四／八／十五／三十秒退避回执查询、六十秒心跳及幂等重试，流程失败后等待一秒再开始下一轮。独立到达率场景继续按目标速率发压。202 只计受理，保存成功以 COMMITTED 及实际答案核对为准。

每次按 20 题上限创建练习，阅读组保持完整，实际题数以练习快照为准。HTTP 成功率、延迟和保存确认指标全程判定。`commit_p95_ms`、`commit_p99_ms` 从首次提交到客户端观察到 COMMITTED，包含重试、排队和回执轮询；命令实际完成数量另外核对。学生流程包含数分钟思考时间，流程成功率按整轮所有已结束流程核对；滚动一分钟窗口监测请求、保存和队列指标。完成吞吐按成功完成事件统计，强制停止时从保留的原始指标补齐实际 VU，结果保留重建标记。

`ready_and_drained_seconds` 记录停压后证实服务就绪、请求结束且队列排空的时间；`audit_seconds` 记录持久化核验耗时；`recovery_seconds` 包含两者及最终复核。各轮同时保留核验前后的计数快照。

各轮结果的 `seed_sha256` 对应实际恢复的数据快照；账号池扩充后会保存新的快照，便于核对同档 A/B 的数据基线。运行配置中的摘要记录初始快照，实际账号规模同时保存在逐轮结果中。各轮从应用指标读取实际并发、等待容量、等待时限和缓存开关，记录在逐轮结果字段；比较缓存与准入策略时同时核对这些值。

吞吐场景每档使用 [k6 独立到达率调度](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/constant-arrival-rate/)，避免响应变慢时自动降低目标发压。未发出的操作以 [dropped iterations](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/dropped-iterations/) 单列；判断边界时同时检查发压端资源与可用 VU，按[官方大规模测试指引](https://grafana.com/docs/k6/latest/testing-guides/running-large-tests/) 区分发压端和服务端限制。

常规判定为成功率至少 99%，各接口 HTTP P95 不超过 2 秒，保存受理 P95 不超过 1 秒，落库 P95 不超过 5 秒、P99 不超过 15 秒，正常队列不持续增长，阻塞积压独立列出。积压比较一分钟内前后半段的均值及连续样本；统计投影按一秒批处理，等待不足五秒的批次波动不计持续滞后。429、5xx、网络错误、未启动迭代和中断流程分别记录。

发生 OOM、容器重启、持续大量失败或就绪检查异常时停止新请求。主机可用内存低于 256 MiB 持续 15 秒、磁盘剩余低于 5 GiB，或管理连接连续两次超时也会停止。本机发压进程达到 CPU／内存保护线时标记为发压端边界，结果作为已测下限。

整套指标采集允许 15 秒；采集失败后另做 5 秒 SSH 探测，分别记录监控边界和管理连接失败。应用就绪状态直接检查 readiness 接口。隔离环境启用 Tomcat MBean 指标，停止负载后等待业务 HTTP 线程归零、已登记命令和统计事件消化，以及三项应用重新就绪；持久化计数须连续两次采样保持一致。审计后再次读取计数，若期间有请求完成则重新等待并核对，整个过程限于十分钟。恢复时间包含静默确认和审计，并保留阶段采样。

私有隧道使用 AsyncSSH 的异步转发，在独立连接内将 SSH 会话的文件句柄软上限核验并提高到至少 32768，保留原硬上限。该设置随测试连接结束，SSH 守护进程及其他会话沿用各自配置。控制器持续检查隧道进程；进程退出时停止发压，原因记录为 `private_tunnel_exited`，并单列退出码。链路退出产生的失败不能据此认定为服务器容量边界。

发压端记录 k6 及转发进程的 CPU、内存。k6 CPU 按 Mac 全部逻辑核归一化；异步转发 CPU 以单核为 100%，持续十五秒达到 90% 时记录 `generator_tunnel_cpu_ceiling` 并停压，以识别转发端先饱和的情况。

当前本地判题协议的目标验证分为 1800 人持续练习、集中交卷、集中恢复网络和内容版本更新，同资源、同数据对照；稳定档三十分钟且完整对账通过后再进入 2000 人。每轮分别报告本地等待、HTTP 受理、服务端提交及回执可见延迟，报告提交／查询准入拒绝与正常／阻塞积压。本地稀疏保存和 SQL 执行计划不代表远端并发容量。

## 恢复与证据

每次运行将发送意图与服务器登记记录匹配，核对全部已登记命令、最终回执、实际答案、标记和成绩；请求超时但服务器已受理的命令也参与核对。客户端收到的受理数量、服务器新增记录和未匹配记录分别列出，存在未匹配登记时不通过一致性检查。运行目录保存压缩 HTTP 指标、主机及容器/JVM/连接池/队列采样、命令账本和逐次结果。账本包含模拟用户的写入凭证，保留在私有目录中。

已完成的逐次结果可在配置匹配时复用，保留原始指标和原压测工具摘要；后端版本、场景、档位、限流和时长必须一致。未完成运行保留现场，不能作为完成档位复用。

`--restore` 在退出时恢复原基础服务与应用配置，并校验原配置摘要。套件完成后清理带本次运行标签的临时容器、卷和凭据文件；异常中断时保留临时数据供诊断。独立的服务器计时器在五分钟未收到测试端心跳后尝试恢复原服务，降低发压机离线造成的影响。

```sh
"$CAPACITY_PYTHON" tests/capacity/report.py --state "$CAPACITY_STATE" --output tests/capacity/results/<运行编号>
```

导出报告包含中文说明、CSV、JSON 和可交互 HTML 图表。连接参数和令牌留在私有目录。报告区分已验证稳定容量、首次失稳、容器失败以及发压端／链路限制；公网全链路容量需要独立验收。

报告资源趋势包含主机 CPU、可用内存、网络发送、容器 CPU/内存、JVM 堆与 GC、连接池等待、数据库锁等待、答案队列和统计投影，以及 HTTP 等待人数、等待耗时、缓存命中／回源和 Redis 内存、连接及淘汰。服务端 P95 使用直方图桶上界估计，结合客户端 P95 判断应用处理与测试链路耗时。

